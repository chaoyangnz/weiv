# Compiler model and operation boundaries

A model describes persistent compiler data. An operation reads identified inputs
and constructs or updates identified outputs. Directory placement follows the
phase that owns those representations.

## Classification

| Responsibility | Owns | Dependencies |
| --- | --- | --- |
| Model | Stage records, tagged payloads, spans, IDs, collections and ownership invariants | Shared value types and other models |
| Operation | A pass, its private work state and pass-specific failure contract | Input/output models and the helpers needed for that pass |
| Boundary operation | Foreign transport or wire-format validation and its errors | Boundary APIs, standard libraries and shared value types |
| Coordinator operation | Pass ordering and transfer of compilation ownership | The operations it composes |

Models may provide pure queries and invariant checks. Source scanning,
normalization, JSON decoding, filesystem access and foreign calls belong to
operations. A model must not import a pass, JSON parser or FFI implementation.
Operations may declare their own private tasks/cursors and error enums; those
are implementation/failure contracts rather than persistent stage models.
Shared errors get their own module when several passes need the same contract.

The JSON field aliases are scoped to the decoder's live JSON DOM. Returned
script facts own their containers and retain strings independently of that DOM.
The normalizer leaves raw storage unchanged. The directive split operation
mutates only the document being built by the parser. None of these compiler
passes resolves files or imports from disk.

## Naming and dependency direction

Representation files use domain nouns: `ast`, `normalized`, `script_facts`,
`decoded_script`. Compiler-pass files use verbs: `parse`, `normalize`,
`split_directives`, `decode_script_facts`. Directories disambiguate repeated pass
names such as the SFC and template parsers. Avoid generic `types`, `operations`,
`common` or `utils` modules.

Named boundary modules (`script_json`, `script_backend`) are operations with an
explicit boundary contract. Their names identify the format/service they adapt.
They may own boundary errors and helpers; persistent AST/SIR data lives in model
modules. The decoder imports `script_json` as `validation` to express that role
at call sites. The native bridge C file is private transport implementation.

```text
full-file bytes → SFC parse → SfcDocument
template bytes → template parse → TemplateDocument → normalize → NormalizedDocument
script/path strings → Rust transport → JSON → decode → DecodedScript
                                                    (ScriptFacts + separate code)
```

The compilation owner uses SFC section spans to supply template/script bytes
from the same retained source. It will keep raw and normalized documents paired.
Imported component manifests will be supplied to binding explicitly;
filesystem/project resolution stays outside semantic binding.

## Slot manifest contract

Manifest discovery visits ordinary descendants, both conditional branches and
loop bodies in preorder. It records each outlet and skips that outlet's entire
fallback subtree, matching Zig. Runtime conditions are not evaluated and loops
are not expanded. Every occurrence is retained; each later duplicate gets one
report with its own source span. A null/default slot differs from an explicitly
empty name. Named lookups use exact UTF-8 equality.

Names are detached from source/raw storage. Manifest queries are pure model
queries; indexed read-only borrows avoid Cyna LG-58's for-binding lifetime bug.
The build pass reads its inputs without mutation and can run repeatedly. A future
imported-component provider supplies manifest data explicitly; neither the model
nor the build pass opens files.

## Binding contract

Template binding is a pure operation over explicitly supplied data. An imported
component catalog is separate from lexical resolution: visibility comes from
ScriptFacts, loop scopes and builtin emit; optional child-slot validation comes
from the catalog. No provider callback opens files during binding. The project
resolver will construct the catalog beforehand and handle its own failures.

Expressions retain template source spans; names and diagnostic text are detached.
Every binding diagnostic has a BindingSource origin: ordinary diagnostics are
template-relative, while reserved script-binding diagnostics are script-relative.
The binder walks every normalized node, including outlet fallback, while the
own-slot manifest keeps its established fallback exclusion rule. Iterables bind
before their aliases enter scope; scope ends follow normalized subtree ranges.
Component slot validation inspects direct children, with structural wrappers
classified as unnamed content as in Zig.

The current scanner preserves Zig's ASCII identifier/keyword/quote/template-
string rules, property/spread handling, reference dedup/call upgrades and helper
warning policy. It is a lexical binding pass, not a JavaScript parser. Diagnostic
identifier locations retain the reference implementation's node-span-relative
offset arithmetic; precision improvements are a separate compatibility change.

Pass-private LoopScope records live in binding_context.cy. Persistent bound
records live in template_bindings.cy. The own manifest transfers out of its
build report through explicit named-field replacement capture, preserving one
owner for its list. Read-only owned-record access uses indexed borrows (LG-58).

## Adding the next stage

Before implementation, identify the model a stage owns, the models/source it
reads, whether inputs remain immutable, the lifetime of returned IDs/views and
its failure contract. Put the algorithm in its operation module and persistent
records in the owning model module. Apply the same distinction to slot manifests,
template bindings, lowering and browser representations as those stages arrive.


Browser lowering accepts the frontend's LIR forest invariant: every arena node
is reached exactly once through root/child/provision edges, with no cycles or
shared nodes. It preserves that invariant and the node IDs in RenderDocument.
Logical traversal order, rather than arena order, defines reference allocation.
Browser tree construction does not add a backend stage to the target-neutral
component coordinator; consumers invoke it after obtaining a complete unit.


## JavaScript emission contract

Emission is separate from BrowserComponent assembly. JavaScriptModule owns code,
scope ID and CSS; import overrides are explicit input data. Shared JavaScriptError
is a failure contract, not a persistent compiler representation. Static emission
validates the whole render forest before CSS/backend work, so unsupported dynamic
nodes/effects cannot produce an apparently complete partial module.

The static API deliberately uses empty managed-cell and local subscription
selections, matching Zig's explicit selection API. It is not the project driver
or managed-state selector. Script setup still uses real Rust cell lowering via
scoped FFI transport. A separate strict decoder validates code/error fields and
maps every known failure category; malformed responses do not become empty code.

Shared output/import/metadata operations are reusable by subsequent dynamic
emitters. Immutable runtime fragments and the complete entity inventory live in
Cyna source without runtime generation. Static createDom uses iterative
enter/finish work records with optional parent reference IDs, existing render reference IDs, scope markers and
reference-compatible entity/namespace behavior. Keep dynamic evaluator/cell
planning separate from DOM operations and artifact models when adding updates.

Operation-private work records use distinctive domain names such as StaticDomVisit.
This avoids Cyna LG-64's confirmed generic specialization collision with the
existing private Visit in browser lowering. Explicit return in void!Error
validators avoids installed lowering failure LG-63; both reports live only in
Cyna's LANGUAGE_GAPS.md.


## Evaluator planning and fixed DOM updates

build_evaluator_plan reads original template bytes, RenderDocument and ScriptFacts,
validates through the retained Rust predicates and returns an owned EvaluatorPlan.
It follows logical edges with explicit loop-entry/exit work state, so IDs agree
with the reference independently of arena order. Each record maps a typed site
and node/effect index to a closure ID and exact source/generated ranges. The
original render tree and graph remain unchanged. emit_evaluator_call accepts a
record and scope expression; hidden NUL-prefixed source markers are unnecessary.

The module emitter supports nested elements with fixed topology, interpolation,
binds and events. DOM creation uses existing reference IDs and typed event records;
update emission pairs planned text/binding sites with original regions, validating
provenance before emitting full/selective calls. emit_binding_update owns binding
semantics and identifier suffix writing. Region guards preserve precise imported
binding/path behavior. Script lowering and setup share the evaluator code without
filesystem lookup or implicit managed-state selection. Static validation delegates
to the same module assembly; structures remain gated until their emitters arrive.
